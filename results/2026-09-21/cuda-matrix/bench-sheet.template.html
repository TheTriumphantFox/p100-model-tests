Keep the incumbent. Nothing displaced it.

Qwen3.6-27B-Uncensored-HauhauCS-Aggressive Q5_K_M holds the best score in every accuracy column, and it is the only model that finishes all 14 reasoning batches instead of running out of thinking budget partway through. Sixteen models have now been measured on this machine; none of them beat it on any test.

The fast-and-accurate combination does not exist
The ggml-org Q8_0 runs at 22.7 tok/s with its matching drafters — 2× the incumbent — but codes at 95.73 against 96.34. The speed is real; the accuracy gain was wishful.
Our best reasoning score was a fluke
GPT-OSS-20B was on record at 77.14. Run five times it scores 71.43 in four of them — an exact tie with the incumbent. It is also the only model whose answers change between identical runs.
The production model is finally measured — and it is the wrong test for it
devstral-patched loads fine, runs at 12.9–13.1 tok/s, and scores 84.76 coding and 58.57 quick — the coding gap against the incumbent is real (p<0.001). It has no thinking mode. But every column here is single-turn Q&A, and what production asks of it is agentic tool use, which nothing here measures. Do not read this as “replace it”.
Three shelf models cannot run here at all
Not “scored badly” — they fail to load on this build. Including opus-distill, kept specifically to verify a 75.7 claim that therefore cannot be checked.

Can the numbers be trusted?

Yes, with one named exception. The same measurement was repeated to see whether it returns the same answer twice.

The thinking column is bit-reproducible

The incumbent's 44,201-token thinking run was executed three times across two days and returned an identical score, an identical token count and identical per-question answers every time. An earlier worry — that long generations might carry variance exceeding the gaps being compared — is refuted.

GPT-OSS-20B is the exception

The only model that gives different answers on identical repeats. Two of its runs scored the same while disagreeing on which questions they got right. Its 77.14 record reproduced under no setting tried — including letting it think three times harder, which made it worse (60.00).

How much context fits?

The worry was that the big Q8_0 files could not hold a useful conversation. They can, easily — and two numbers in the earlier notes were wrong.

ModelKV per token Largest testedVRAM spare

Every model stayed fully resident at every size tested, with decode speed flat to two decimals — context costs memory here, never speed. 32,768 was the largest size tried, not the ceiling; no spill boundary has been found.

KV is 72 KiB/token, not 260

Measured by VRAM difference across context sizes. The earlier figure was wrong by 3.6×. On its spare memory the incumbent could hold roughly 180,000 tokens of context — we have been running 8,192.

G9v3's context advantage is 1.6×, not 7×

46.0 KiB/token against the dense models' 72.0 — not the 38-vs-256 used to justify keeping it. Still the cheapest measured, but not on its own a reason to keep a model.

Why three models produce no numbers

Each fails at model load with its own error. The file is intact in every case — the runtime is what cannot handle it.

ModelLoad errorDiagnosis
Gemma4-E4B-Abliterated Q4_K_M wrong number of tensors; expected 2131, got 720 Header and file both hold 2131. The gemma4 loader maps only 720 — an E4B architecture support gap.
Qwen3.6-27B Opus-Distill Q4_K_M tensor 'blk.0.ssm_dt.bias' not found Carries vision.block_count 27 and 1292 tensors — it is a vision model, not the text distill our notes describe.
Qwen3.6-35B-A3B-Abliterated-VL Q4_K_M rope.dimension_sections has wrong array length Multimodal RoPE sections the text-only loader cannot parse.

The incumbent is the control: same qwen35 architecture, same block_count 64, same SSM keys — but 851 tensors and no vision block, and it loads. Both Qwen failures carry their vision tower inside the single GGUF, and their ollama manifests list exactly one model blob with no separate projector, so this cannot be fixed by re-pointing a symlink.

What is still not done

  1. Nothing here measures agentic tool use — which is the entire job devstral does in production. All four columns are single-turn question and answer: one question in, one answer out, marked right or wrong. Devstral's own prompt template carries a tool-calling section, and the local patch that gives it the -patched name is a fix to that section for agentic clients. So its scores below say little about whether it is the right model for its job, and “devstral scores under the incumbent” is not an argument for replacing it. Closing this needs a tool-use harness, which does not exist here.
  2. Three models need a newer or patched runtime before they can be tested at all.
  3. The wider 280-question exam is built but not run, waiting on which models deserve it. It will need the incumbent re-run as a fresh baseline: it draws different questions — only 9 of the current 70 overlap — so its scores cannot be compared with anything above.
  4. Refusal behaviour is unmeasured too. This round sharpened why — the quick exam cannot even tell an uncensored model from a stock one. Three Qwen3.8 variants gave identical answers to all 70 questions, so it is no evidence either way.
  5. Production can probably hold twice the context it runs, for free. Devstral measured 168 KB per token of context at f16 — about 84 KB at the compressed q8_0 production uses — which leaves roughly 4,400 MB unused at its current 49,152 setting and puts the ceiling near 100,000 tokens. Raising it to 65,536 costs nothing. Confirm the compressed figure with ctx-ladder.sh first: it is the measured f16 number halved, not separately measured.
Settings — identical to the previous two rounds, so old and new numbers are comparable. MMLU-Pro: 70 questions (5 per category × 14), seed 42, temperature 0; quick at 8,192 context, thinking at 16,384 context with a 12,288-token budget. HumanEval: all 164 problems.
