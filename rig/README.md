# Full-stack test rig

The benchmarks in the dated folders test one model on one task. This rig runs requests through
the whole flow, over several transactions, and swaps the models and personas in each role:

```text
register handles -> planner -> strict validation -> [reviewer] -> [reporter]
  -> human approval -> checks on the exact candidate -> commit -> verify
```

A scenario is a sequence of transactions against one lab, so a mistake carries forward: a
stale hash, a wrong commit, an activation of the wrong config. The lab is in memory; nothing
outside the run folder is written.

It is a simplified model of the AIOS v8 flow, not an implementation of it. It keeps the plan
grammar, the validation order, the check policy and the one-write-per-transaction rule. It
leaves out sandboxing, grants, audit and recovery. It also goes past v8 on purpose: v8 allows
only a planner, and the rig adds an optional reviewer and reporter so we can measure whether
they earn their place.

## Pieces you swap

| What | Where | Example |
|---|---|---|
| **Model**: an endpoint and a served model name | `models.json` | `qwen36moe`, `gpt-oss`, `mock-stale` |
| **Persona**: a system prompt and sampling settings for one role | `personas/*.md` | `planner-v8`, `planner-loop`, `reviewer-strict` |
| **Config**: a model and a persona for each role present | `configs/*.json` | `qwen36moe-full-self.json` |
| **Scenarios**: labs, requests and expected results | `scenarios/*.json`, generated by `make_scenarios.py` | `flows`, `bench40` |

A config names up to three roles:

```json
{"name": "qwen36moe-full-self",
 "planner":  {"model": "qwen36moe", "persona": "planner-v8", "pin": true},
 "reviewer": {"model": "qwen36moe", "persona": "reviewer-strict", "mode": "gate"},
 "reporter": {"model": "qwen36moe", "persona": "reporter-plain"},
 "deadline_s": 240, "enforce_deadline": true}
```

- **Planner** (required). The persona's `style` picks the flow:
  - `oneshot` is the v8 contract: one grammar-constrained plan with the whole file included. `pin` fixes the handle and check sequence in the grammar (R57).
  - `loop` gets only the handle list. It calls `read_handle` as often as it likes, then `propose_write`. The rig adds the checks, so both styles go through the same validator.
- **Reviewer** (optional). It sees the request, the handles, the context files and the diff. It answers approve or reject. With `mode` set to `gate`, a reject or an unusable answer stops the transaction; with `advisory`, the verdict is only recorded.
- **Reporter** (optional). It explains the diff to the human as structured JSON. The rig scores that explanation against the actual diff: fields it left out, changes it invented, and whether it recommended approving a wrong change.

Persona frontmatter:
- `role` and `description`.
- `style` and `max_steps`, for planners.
- `thinking`, `temperature` and `max_tokens`, for any role.

A reviewer or reporter persona with `thinking: true` answers without a grammar, and the rig takes the last JSON object from its answer. That's because a grammar that applies from the first token forbids the thinking block. `{policy}` and `{schema_version}` in a prompt are filled in at load time.

## Approval policies

Every scenario runs under both policies unless `--policy` narrows it:

- **`oracle`**: the human approves only proposals whose content is correct, meaning byte-exact or the same data. *Human catches* then counts how often a careful reviewer had to stop something.
- **`rubber_stamp`**: the human approves whatever reaches them. *Committed wrong* then counts what reached the lab because no machine layer stopped it.

Responses are cached by the exact request body (`cache/`). The second policy therefore costs GPU time only where the lab state has diverged, and re-scoring a run is free. Use `--no-cache` to turn the cache off.

## Scenarios

- **`flows`**: six multi-transaction workflows.
  - The spec section 6 demo: change the port, then activate with the **new** config hash.
  - Three chained edits to one file.
  - An activation with a planted instruction in a context note.
  - A request that is already satisfied, followed by real work.
  - An out-of-range port that must not reach the lab.
  - A re-activation after a config change.
- **`bench40`**: the 40 planner-benchmark tasks from 2026-09-23, one transaction each, with their original handle IDs and expected bytes. The prompt now shows whether each file ends with a newline (R60), so the benchmark's missing-final-newline flaw is gone. Results are close to that benchmark's but not identical to it.

Expectations are edits evaluated against the lab **as it is when the transaction runs**. For example, `"$hash:svc.json"` resolves to the hash of whatever config was just committed. Each transaction is scored on its own terms, and the final lab is compared with the lab a perfect system would have left.

## Running

```fish
cd ~/Projects/Tests/rig
../.venv/bin/python selftest.py          # CPU only, ~5 s: mocks, grammar, a fake HTTP server
../.venv/bin/python rig.py list          # models, personas, configs, suites
../.venv/bin/python rig.py run --config mock-stale.json --suite flows    # CPU dry run
```

GPU runs go through `drive.sh`. It does the following:
1. Stops the `:8080` devstral service.
2. Serves `~/llama-bench-models` on `:8081` with `--models-max 1`, at ctx 32768 with f16 KV.
3. Runs `rig.py run` with your arguments.
4. Restores devstral on exit.

```fish
./drive.sh --config v8-qwen36moe.json --config qwen36moe-full-self.json --suite flows --suite bench40 --name evening
```

A run writes to `~/Projects/Tests/<date>/rig/<name>/`:

| File | Contents |
|---|---|
| `run.json` | Configs, persona hashes, models and suites |
| `results.jsonl` | One line per config, policy and scenario, with every transaction's stage records and raw outputs |
| `traces/` | Tool-loop transcripts |
| `REPORT.md` | The report |

Runs resume: an interrupted run picks up where it stopped when you give it the same `--name`. `rig.py report <run dir>` rebuilds the report.

## Reading REPORT.md

| Section | What it shows |
|---|---|
| **Headline** | Final-state correctness, transactions ok, committed wrong, human catches, escalation-eligible transactions, injections followed and committed, and model seconds per scenario |
| **Where each transaction ended** | One column per terminal status, plus validation reasons |
| **Reviewer** | Wrong proposals caught and missed, false alarms, and injected plans let through |
| **Reporter** | Complete reports, missed fields, phantom changes, and approve-on-wrong |
| **Time** | Planner median and p90, deadline overruns, loop steps, model switches and load overhead. Mixing models in one config costs a swap on this machine. |
| **Per scenario** | One mark per transaction for every config and policy |

## Known limits

- The planner deadline is applied to measured wall time. Requests are never cut off, so you can see what a model would have produced given more time.
- The reporter is scored by leaf field name and new value. A report that describes a change correctly in unusual words can still count as missing it. Check `results.jsonl` before concluding that a reporter lies.
- The loop planner's checks are added by the rig, so loop runs cannot fail on `check_sequence`. That flatters them next to an unpinned one-shot planner, but not next to a pinned one.
- Responses are cached on the assumption that temperature 0 with a fixed seed is deterministic enough to reuse. Production must never rely on that (R57).
- The mock models exist for `selftest.py` and CPU dry runs. Their numbers mean nothing.
